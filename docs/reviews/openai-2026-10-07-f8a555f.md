Major, app/views/context_menus/_itil_priority.html.erb:11 and :23
Impact/Urgency entries in the issue context menu are disabled whenever any selected issue is “priority_derived?”, which (in this plugin’s terminology) means the priority is linked to Impact×Urgency. That disables changing Impact/Urgency for linked issues via the context menu, even though this is exactly what helpdesk users (without the override permission) are supposed to be able to do, and what operators should also be able to do when linked.
Failure scenario: A helpdesk user right-clicks a linked issue to change Urgency from Normal to Urgent. The Impact/Urgency submenu entries render but are all disabled because @issues.any?(&:priority_derived?) is true, preventing classification from the list view. This contradicts the documented behavior and the form behavior, where Impact/Urgency remain editable when linked.
Fix: Remove the priority_derived? part from the disabled condition for the Impact and Urgency menu items. Keep only the edit capability check, and let the backend safe_attributes enforce who may set priority/unlink. For example:
- disabled: (!@can[:edit] || @issues.any?(&:priority_derived?))
+ disabled: !@can[:edit]
Alternatively, if priority_derived? was intended to guard the old direct “Priority” submenu, apply it only to that (not to Impact/Urgency).

Resolution: not a defect. priority_derived? is core's Issue#priority_derived? (`!leaf? && Setting.parent_issue_priority == 'derived'`): a parent issue whose priority comes from its subtasks, the same condition core's own Priority submenu uses. It has nothing to do with this plugin's link; for ordinary issues the Impact/Urgency entries are enabled (issue_list.mjs sets the urgency through the context menu; context-menu screenshots in docs/e2e show them enabled for the helpdesk user).

Minor, .github/workflows/redmine-tests.yml:82-87 (upload-artifact step)
The workflow uploads redmine/log/*.log as an artifact for e2e runs. Rails logs can include sensitive information (request parameters, possibly API keys if logged, webhook endpoints, etc.). This violates the “no secrets in logs” rule and can leak credentials from manual CI runs.
Failure scenario: A manual CI run executes e2e that exercise REST API or webhooks. If logging level or middleware logs headers/params, the API key or webhook secret ends up in redmine/log/production.log and is uploaded as a publicly retrievable artifact.
Fix: Stop uploading logs or filter them. Options:
- Remove redmine/log/*.log from the artifact path.
- Or redact logs first (e.g., grep -v sensitive headers/params) and upload the redacted copy.
- Or ensure logging level excludes parameters and headers during CI (e.g., REDMINE_LOG_LEVEL=info, and Rails.filtered_parameters includes API keys), and still prefer not uploading logs.

Resolution: the known point for the migration kit's manual CI workflow (plan, item 18); not changed here. Nothing new accepted: the review loop stops.
