Major, lib/redmine_itil_priority/patches/issue_patch.rb:12
Impact and urgency are always safe attributes when the issue is editable, even when ITIL priority is inactive for the issue’s project/tracker. This lets users set impact_id/urgency_id via context menu, bulk edit, REST API and mail on trackers explicitly set to “inactive,” despite the UI hiding the ITIL form there.
Failure scenario: Project A, tracker “Support” set to “inactive” in the project ITIL settings. A member opens the issue list, uses the context menu Bulk edit to set Impact/Urgency on Support issues. The changes are accepted and journalized although ITIL is inactive for Support; priority does not follow the matrix (settings_for_mapping is nil), leading to confusing history/filters and stored stale values that resurface if ITIL is later enabled.
Fix: gate the fields on ITIL activation, not just general editability. For example:
- In the safe_attributes declaration, require that settings are active:
  safe_attributes 'impact_id', 'urgency_id', if: ->(issue, user) { (issue.new_record? || issue.attributes_editable?(user)) && RedmineItilPriority.settings_for(issue.project, issue.tracker).present? }
- Additionally, in safe_attribute_names, when ITIL is inactive (no settings), remove impact_id/urgency_id from the returned list:
  def safe_attribute_names(user = nil)
    names = super
    unless RedmineItilPriority.settings_for(project, tracker)
      names -= %w[impact_id urgency_id itil_priority_linked]
      return names
    end
    …existing logic…
  end

Resolution: fixed in the commit after fae24d3 ("Impact, urgency and the link not assignable where ITIL is inactive"): safe_attribute_names drops impact_id, urgency_id and itil_priority_linked where settings_for is nil. Pre-existing behaviour (master had them always safe). Tests: test_impact_urgency_and_link_are_not_assignable_where_itil_is_inactive, test_impact_and_urgency_are_not_assignable_without_the_module (both fail without the fix).

Major, app/views/context_menus/_itil_priority.html.erb:1-16
The context menu shows “Urgency”/“Impact” submenus whenever @safe_attributes includes the respective field, regardless of whether ITIL is active for the selected issues. Combined with the issue_patch behavior above, this exposes Impact/Urgency editing on trackers set to “inactive”.

  and the same for impact. This should be paired with the safe_attribute fixes above.

Resolution: no change needed. With the fix above @safe_attributes no longer contains the fields for inactive issues either.

Major, lib/redmine_itil_priority/patches/issue_patch.rb:86-108 (PrependedMethods#safe_attribute_names)
itil_priority_linked remains mass-assignable when ITIL is inactive. The override removes priority_id/itil_priority_linked only if RedmineItilPriority.settings_for(project, tracker) is present; when inactive, itil_priority_linked is still accepted and stored.
Failure scenario: On a tracker where ITIL is inactive, an API client sends {itil_priority_linked: false, priority_id: <any>}. The request succeeds; the flag persists (false). Later, when ITIL is enabled for the tracker, that existing issue unexpectedly starts “unlinked” instead of the intended default “linked,” violating the post-upgrade expectation that existing issues behave as before unless changed under ITIL.
Fix: always reject itil_priority_linked unless ITIL is active and the user can actually override the priority. Extend the early return in safe_attribute_names to strip the flag when inactive (see the first finding’s fix), and keep the existing “must include priority_id and permission” requirement when active.

Resolution: fixed by the same change as the first finding (the flag is dropped where ITIL is inactive); covered by the same test.

These logs can include sensitive parameters (e.g., the /mail_handler API key “key=…”, Basic auth usernames, webhook URLs) from the test runs. This violates the “no secrets in logs” rule and risks accidental exposure in CI artifacts.
Failure scenario: A manual workflow run with e2e enabled uploads production-mode logs that contain the mail handler key used in tests and request headers/URLs. The artifact is accessible to anyone with repo access and can be persisted beyond the run.
Fix: stop uploading logs, or at least mask/filter sensitive parameters before upload. For example, remove redmine/log/* from the artifact path; or set Rails/Rack parameter filtering to include :key and avoid logging headers, and only upload docs/e2e/. If logs are needed for debugging, gate the upload behind a separate boolean input (off by default) and ensure secrets are filtered.

Resolution: not changed here. The workflow is the migration kit's manual-only CI file (shared with the other plugins), and the logs of that throwaway CI instance hold only test credentials made up for the run (mail handler key "e2e-mail-key", seeded test logins; Rails already filters password parameters). Recorded in docs/REDMINE7-MIGRATION.md as a point for the kit: drop or filter redmine/log in the artifact.
