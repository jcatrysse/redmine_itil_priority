Major, lib/redmine_itil_priority/patches/issue_patch.rb:61-101
Problem: Order-dependent safe assignment lets impact/urgency slip through on trackers where ITIL is inactive if tracker_id arrives later in the same payload. safe_attribute_names decides whether to allow 'impact_id'/'urgency_id' based on RedmineItilPriority.settings_for(project, tracker). During create/update, tracker may still be nil or the old value when safe_attribute? is evaluated for these fields, because safe_attributes= does not ensure 'project_id'/'tracker_id' are applied first. A malicious or simply differently-ordered API client (or incoming mail) can send impact_id/urgency_id before tracker_id; if settings_for(project, nil) (or for the previous tracker) returns truthy, the values are accepted, even if the final tracker has ITIL priority inactive.
Failure scenario: In a project where ITIL priority is inactive for Tracker A but active by default, POST /issues.json as a reporter without override permission with JSON body:
{ "issue": { "subject": "x", "impact_id": "3", "urgency_id": "2", "tracker_id": A } }
If impact_id/urgency_id appear before tracker_id, they get assigned because settings_for(project, nil) is truthy; the created issue on Tracker A illegitimately stores impact/urgency though ITIL is inactive there.
Fix: Make assignment order robust:
- In safe_attributes=, reorder so that 'project_id' and 'tracker_id' (and possibly 'status_id') are applied before any ITIL fields, then apply 'itil_priority_linked', then the rest, and 'priority_id' last. For example:
attrs = attrs.to_unsafe_hash if attrs.respond_to?(:to_unsafe_hash)
ordered = attrs.slice('project_id', 'tracker_id').
            merge(attrs.slice('itil_priority_linked')).
            merge(attrs.except('project_id','tracker_id','itil_priority_linked','priority_id')).
            merge(attrs.slice('priority_id'))
super(ordered, user)
- Alternatively (and additionally defensive), have safe_attribute_names treat a nil tracker as inactive for ITIL by consulting any incoming attrs['tracker_id'] (available only in safe_attributes=), or by returning names - %w[impact_id urgency_id itil_priority_linked] when tracker is nil. The first approach (reordering) avoids false negatives on creates where ITIL is active.

Resolution: not a defect, proven with a test instead of changed code. Core's Issue#safe_attributes= takes project_id, tracker_id and status_id out of the hash and assigns them first (and sets a default tracker when none is given) before delete_unsafe_attributes runs, so safe_attribute_names for impact_id/urgency_id is evaluated against the final tracker whatever the key order. test_key_order_cannot_set_impact_on_an_inactive_tracker (override_itil_priority_test.rb) sends impact and urgency before tracker_id to an inactive tracker: not stored; to an active one: stored.

Problem: The workflow uploads redmine/log/*.log as an artifact on e2e runs. Redmine logs routinely include request headers (API keys in X-Redmine-API-Key), mail handler payload excerpts, and SMTP errors. Even if tests currently use throwaway credentials, this is an avoidable exposure and contradicts the “no secrets in logs” rule.
Failure scenario: A contributor mistakenly runs the manual workflow against an environment that points at a non-throwaway mail server or uses a real API key in tests; the key and other sensitive data end up in the uploaded artifact accessible to anyone with repo access.
Fix: Stop uploading logs or filter them:
- Remove redmine/log/*.log from the upload path; or
- Upload only docs/e2e/ and, if logs are needed, a redacted copy produced by grep/sed that strips API keys and email addresses.
