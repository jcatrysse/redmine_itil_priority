## Part 2 of 2

Major, test/unit/settings_cache_test.rb:27
Problem: update_all writes a deserialized Ruby Hash into a text column for a serialized Setting. record.read_attribute(:value) on a serialized attribute returns the cast object (Hash), not the serialized string. update_all bypasses AR serialization, so on some adapters this will either raise or write an unparseable string, breaking subsequent Setting loads.
Failure scenario: On PostgreSQL, update_all(value: <Hash>) can lead to quoting via to_s (e.g. {"k"=>"v"}), which is not valid YAML/JSON for Redmine’s Setting serializer. After Setting.check_cache, Setting.plugin_redmine_itil_priority may fail to load or return a String instead of a Hash, causing follow-up assertions (and potentially other tests) to error or behave inconsistently across DBs.
Fix: Pass the serialized value. For AR serialized attributes use read_attribute_before_type_cast to get the raw stored string, or explicitly dump: 
- Setting.where(id: record.id).update_all(value: record.read_attribute_before_type_cast(:value), updated_on: 1.minute.from_now)
or
- Setting.where(id: record.id).update_all(value: YAML.dump(record.value), updated_on: 1.minute.from_now)

Resolution: not a defect. Setting does not use ActiveRecord `serialize`: Setting#value= dumps the Hash to YAML itself and writes that string with write_attribute (app/models/setting.rb, 5.1 to 7.0), so read_attribute(:value) returns the YAML string and update_all stores exactly what a save would. The test then reads the changed value ('8') back through Setting and passes on PostgreSQL 16 and MariaDB 10.11 (and on Redmine 5.1), which it could not if the stored value were unparseable.
